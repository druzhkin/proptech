# PropTech Pipeline — Спека итогового результата
# Версия 1.0 | Март 2026

---

## КОНТЕКСТ

Telegram-канал о PropTech/ConTech на русском языке для профессионалов рынка недвижимости.
Пайплайн должен ежедневно автоматически собирать, отбирать, генерировать и предлагать к публикации
3–7 постов с минимальным участием администратора.

Целевая аудитория канала: девелоперы, инвесторы, tech-директора в недвижимости.
Тон: деловой, конкретный, без воды. Не новостная лента — аналитика и смысл.

---

## ИТОГОВЫЙ РЕЗУЛЬТАТ (что должно работать)

### R1. Сбор контента (collect.py + клиенты)

**Perplexity:**
- Собирает 5–15 релевантных новостей PropTech/ConTech за последние 7 дней
- Использует модель sonar-deep-research
- Корректно парсит ответ: title, url, text, image_url, date
- Retry при rate limit (3 попытки, экспоненциальный backoff)
- Если нет новостей → берёт темы из `config/evergreen_topics.json`

**YouTube:**
- Мониторит все каналы из `config/channels.json` (у них должен быть channel_id)
- Собирает видео за последние 14 дней
- Получает транскрипт (youtube-transcript-api, язык: ru или en)
- Если транскрипт недоступен → берёт description видео
- Дедупликация по URL внутри одного запуска

**Общее:**
- Дедупликация по URL между Perplexity и YouTube
- Результат: `data/articles/YYYY-MM-DD.json` с unified schema
- Логирование количества собранных статей по источникам

---

### R2. Генерация постов (generate.py + claude_client.py)

**Фильтрация:**
- Claude анализирует все статьи и отбирает топ-5 наиболее ценных
- Критерии: новизна, релевантность PropTech, практическая ценность для аудитории
- Не берёт рекламный контент, джобборды, кликбейт

**Генерация поста:**
- Длина: 150–300 слов (оптимум для Telegram-канала)
- Структура: факт/событие → почему важно → что это значит для рынка
- Эмодзи: 1–2 тематических в начале, не перегружать
- Без markdown-разметки (Telegram это не поддерживает)
- Ссылка на источник в конце
- Категория: PropTech / ConTech / Инвестиции / Регулирование / Тренды

**Валидация поста:**
- Проверка длины (< 400 слов)
- Проверка наличия ссылки
- Проверка: нет markdown символов (#, **, __)
- Если пост не прошёл валидацию → регенерация (1 попытка)

**Результат:** `data/drafts/YYYY-MM-DD.json` со статусами draft/published/rejected

---

### R3. Telegram-бот (bot.py)

**Ревью-интерфейс:**
- `/drafts` — загружает черновики сегодняшнего (или последнего доступного) дня
- Показывает пост с метаданными: источник, категория, кол-во слов, есть ли фото
- Кнопки: ✅ Publish / ✏️ Edit / ❌ Skip
- После действия — автоматически показывает следующий черновик

**Публикация:**
- Если есть image_url: публикует фото + подпись (или фото + отдельное сообщение если >1024 символов)
- Если нет фото: публикует текст
- Сохраняет в `data/published/YYYY-MM-DD.json` с telegram_message_id

**Надёжность:**
- Если фото не загрузилось → публикует без фото (с предупреждением в лог)
- Все ошибки публикации показываются админу, не падают тихо
- `/status` — показывает статистику: ожидает/опубликовано/пропущено

---

### R4. Надёжность и DevOps

**Запуск пайплайна:**
- Единственный entry point: `python pipeline.py` или `make run`
- Последовательность: collect → generate → (бот уже запущен отдельно)
- Каждый шаг независим: если collect упал, generate не запускается
- Возвращает exit code: 0 = успех, 1 = частичная ошибка, 2 = полный сбой

**Логирование:**
- Все модули логируют через `logging`, формат: `%(asctime)s [%(levelname)s] %(name)s — %(message)s`
- Лог-файл: `logs/pipeline-YYYY-MM-DD.log`
- Ротация: хранить последние 30 дней

**Конфигурация:**
- Все настройки через `config/.env` (никаких хардкодов)
- `config/.env.example` содержит все необходимые переменные с комментариями
- При старте: проверка наличия всех обязательных переменных, exit с понятной ошибкой если нет

### R5. Тесты (tests/)

Минимальный тест-suite для критических функций:

```
tests/
  test_collect.py       — дедупликация, парсинг, fallback на evergreen
  test_generate.py      — валидация постов, форматирование
  test_claude_client.py — мокирование API, проверка форматов ответа
  test_bot.py           — логика статусов, find_draft_by_short_id
```

- Все внешние API мокируются (pytest-mock или unittest.mock)
- CI: тесты запускаются при каждом push (GitHub Actions, если настроено)
- Coverage > 60% для src/ (исключая bot.py — сложно тестировать async)

## ИЗВЕСТНЫЕ ПРОБЛЕМЫ (для аудита агента)

Это предполагаемые проблемы — агент должен верифицировать и расширить список:

1. **Нет тестов** — директория `tests/` отсутствует или пуста
2. **Нет pipeline.py** — нет единого entry point для всего пайплайна
3. **Нет логирования в файл** — только stdout
4. **claude_client.py** — нужно проверить retry-логику и обработку rate limits
5. **bot.py** — short_id[:8] может дать коллизии при большом числе черновиков
6. **YouTube транскрипты** — fallback на description не реализован или ненадёжен
7. **Нет валидации конфига при старте** — молчаливый сбой если ключ не задан
8. **evergreen_topics.json** — логика fallback не реализована в collect.py
